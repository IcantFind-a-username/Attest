# Real-data evaluation — 2026-08-29

What the pipeline does when it is pointed at real diffs from real repositories,
measured against ground truth taken from those repositories' own history.

Harness: `evaluation/realdata/` (committed; see `evaluation/README.md` to re-run).

## Corpus

403 single-file Python diffs mined from the history of six real projects
(pygments, requests, flask, black, rich, httpx):

| class | n | construction | ground truth |
|---|---|---|---|
| positive | 218 | a real bug-fix commit applied **backwards**, i.e. the diff that puts the bug back | the `+` lines of that reversed diff are exactly the lines the fix had to change |
| negative | 185 | a real docs/typo/format/refactor commit applied forwards | nothing in it should clear an evidence bar |

Plus a **PR-shape sweep**: 719 whole-commit diffs (every file, every type —
binaries, renames, deletions included) used for the budget and parser numbers.

The positive construction is the acceptance scenario from AGENTS.md ("reintroduce
a fixed crash"), taken from real history at scale instead of hand-planted once.

## What this does and does not cover

No `ANTHROPIC_API_KEY` exists in this environment, so **the proposer was not run
live**. Everything downstream of sampling is the real product path on real data:
diff acquisition, hunk mapping, anchor validation, tier-0 lint corroboration,
dedup, channels, gate, ledger, CLI, `attest verify`.

Where a proposal was needed (the end-to-end runs), it was **replayed** — built
from what git history says the real defect was. That is an *oracle* proposer, and
it is deliberate: it removes the model from the question and asks the one the
model cannot answer — given a perfect proposal on a real diff, what does the
evidence gate do? Model quality, live latency and live cost remain unmeasured
here; D-015's live runs are still the only evidence on those.

## Results

### 1. Hunk mapping — exact on real diffs

650 hunks across the corpus, each checked against the real blob on the diff's new
side (content compared line by line, not just ranges):

| check | result |
|---|---|
| range mismatch | **0 / 650** |
| content mismatch | **0 / 650** |
| range running past EOF | **0 / 650** |
| files silently dropped | **0** |

In the 719-commit sweep, 20 commits contain files that carry no hunk in the map.
All 50 such files are correctly absent — they have no new-side line an anchor
could point at: 34 deletions, 10 binaries, 5 pure renames, 1 empty added file.
No parser defect found.

### 2. Anchor validation — exact path or nothing

Admissibility of the true bug line for the 201 positives that have one:

| what the model emits for `anchor.file` | accepted |
|---|---|
| path exactly as in the diff | **100.0%** |
| same path with backslashes | 100.0% |
| `./`-prefixed | 100.0% |
| **`b/`-prefixed** (`b/src/foo.py`) | **0.0%** |
| **`a/`-prefixed** | **0.0%** |
| basename only | 10.0% |

Line tolerance: anchoring one line low still lands in a hunk 97.5% of the time,
one line high 99.0%. All true lines of a fix are in-hunk 100% of the time.

The `a/`/`b/` result is a live risk, not a hypothetical: `norm_path` strips `./`
and normalizes separators but not the diff's own path prefixes, and the prompt's
"as it appears in the diff, after the `+++ b/` prefix" is the only thing standing
between a correct finding and a silent void. The failure is silent by design
(the candidate is discarded as "anchor not inside any diff hunk").

**17 of 218 real bug fixes (7.8%) are pure insertions** — the fix added lines, so
the buggy revision contains no line carrying the defect. For those, the four-piece
schema's in-hunk anchor rule can only be satisfied by pointing at an adjacent
context line. Omission bugs are structurally awkward for this schema.

### 3. Tier-0 (T channel) — not supported by the data

The factory table awards LR 2.0 for one lint signal near the anchor, 3.0 for two
or more. Measured on real bugs, where "near" is the product's own `ANCHOR_SLACK`:

| | true bug lines | other in-hunk lines | empirical LR |
|---|---|---|---|
| positives (218 cases) | 20.3% carry a signal | 17.6% carry a signal | **1.15** — 95% CI **[0.77, 1.74]** |
| negatives (185 cases) | 10.5% | 10.8% | 0.97 — 95% CI [0.66, 1.38] |

CI is a **cluster bootstrap over cases**, not over lines: lines within a case share
a file and a single lint run, so a per-line bootstrap would be spuriously tight.

The factory value 2.0 sits **above the upper bound of the 95% CI**. On this corpus
ruff proximity carries no measurable evidence that a line is a real defect —
a real bug line is about as likely to attract a lint diagnostic as any other
changed line beside it. Ruff ran successfully in all 403 cases (0 failures), with
each repository's own configuration, so this is not a tooling artifact.

It is also not one number. Per repository the empirical LR ranges from 0.67
(requests — signals are *anti*-evidence) to 3.68 (flask), driven by how each
project configures ruff. A fixed cross-repo constant cannot be right for all of
them.

Cost side: tier-0 is cheap — p50 0.010s, max 0.068s per file. It is not a latency
problem, only an evidence problem.

### 4. The gate — verification is the only thing that decides

Exhaustive enumeration of all 45 channel states the pipeline can reach
(votes 1–5 × tier-0 {0,1,2+} signals × verification {none, failed, reproduced}),
at the default alpha = 0.1:

| | |
|---|---|
| decisions reachable | **`drawer`, `surface` only** |
| `discard` (wealth ≤ alpha = 0.1) | **unreachable** — minimum reachable wealth is **1.0** |
| surface without verification | 0 of 45 states |
| every state with `verification=reproduced` | surfaces (15/15) |
| every state without it, or with a failed reproduction | drawer (30/30) |

Two consequences, one known and one not:

- **Known (D-008):** S·T = 9 < 10 = 1/alpha, so nothing surfaces pre-verification.
  Confirmed on real data.
- **Not in the decision log:** conditioned on the V channel, votes and tier-0
  signals change *nothing*. The decision is a pure function of verification. The
  S schedule (D-007) and the T table are, under factory constants, arithmetic
  that never reaches a threshold — and the `discard` arm is dead code. The
  minimum wealth any candidate can hold is 2.0 (one vote) × 0.5 (failed
  reproduction) = 1.0, which is 10× the discard threshold. Alpha auto-tightening
  makes this worse, not better: it lowers alpha (floor 0.01), pushing the discard
  threshold further away while raising the surfacing bar.

  So `report.py`'s "discarded N certified-false candidate(s)" is structurally
  always 0, and a refuted candidate is never retired — it stays in the drawer.

### 5. End-to-end on real checkouts — a true bug and a false alarm are indistinguishable

Real worktrees, real `git diff`, real ruff, real ledger; the proposal replayed with
full 5-of-5 consensus. Two runs per repository (pygments, requests): one asserting
the defect history actually fixed, one asserting a fabricated null-dereference on a
line from a real docs/refactor commit.

All four runs produced **wealth 3.0, decision `drawer`, nothing said**. After
`attest verify --reproduced`, all four surfaced at wealth 60.0 — the true finding
and the invented one alike, with identical channel evidence at every step.

This is the design working as intended ("宁可不说,不说错" — the tool stayed
silent), and simultaneously the sharpest measurement in this report: **the S and T
channels contribute no discriminating power, so the entire burden of precision
rests on the V channel.** Phase 3's evidence executor is therefore not one feature
among several — it is the only component that can make the gate mean anything, and
red line 3 (generated repro tests can encode the model's misreading) is the whole
risk surface.

Full transcripts: `docs/evaluation/e2e-oracle-2026-08-29.txt`.

### 6. Budget on real PR-shaped diffs

719 real whole-commit diffs, default config (K=5, $0.25, default model):

| | |
|---|---|
| would DEFER before any call | **3.8%** (27/719) |
| estimated cost of the K calls, p50 | $0.108 |
| p90 | $0.139 |
| max | $1.706 |
| largest diff that still runs | 44,299 prompt chars |
| smallest diff that defers | 65,407 prompt chars |

The estimate is dominated by the **output reservation**, not the diff: K × 2000
max output tokens costs $0.100 before a single input character is counted, which
is 93% of the median estimate (input contributes a median 7.1%). The default
$0.25 budget therefore buys ~$0.15 of input headroom no matter the repository,
and DEFER is effectively a fixed ~45 KB diff-size cutoff rather than a spend
control. Under-run is large — real spend settles on actual output tokens, and the
live pygments run in DEVSPEND.md settled at $0.0402 against a reservation of at
least the $0.100 output floor.

## What to do about it

None of this is applied. Every item touches a factory statistical constant or
product behaviour, which ground rule 8 reserves for an owner decision.

Ranked by how much they change what the tool says:

1. **Anchor prefix tolerance.** Accept `a/<p>` / `b/<p>` in `norm_path` when `<p>`
   is a path the hunk map knows and the prefixed form is not. Cheap, removes a
   silent-void failure mode, cannot mis-resolve.
2. **Re-price or retire the T channel.** The data supports LR ≈ 1.0–1.2, not
   2.0–3.0, and the right value is repo-dependent. Either drop T from the factory
   tables until there is evidence for a value, or make it a per-repo measured
   quantity rather than a constant. Red line 4 asks a threshold be shown
   achievable before adoption; this is the same question asked of an LR.
3. **Decide what `discard` is for.** With factory tables it cannot fire. Either
   lower V_FAILED so a refuted candidate can be retired, or remove the arm and the
   "certified-false" line from the report so it stops promising something it never
   does.
4. **Separate the output reservation from the budget knob.** Reserving
   `max_output_tokens` per sample makes the budget a diff-size cutoff. Reserving a
   realistic output estimate (observed outputs are far under 2000 tokens) would
   make `--budget` behave like a spend control.
5. **Omission bugs (7.8% of real fixes) have no anchorable line.** Worth an
   explicit decision: accept the context-line anchor, or acknowledge the class is
   out of scope.
