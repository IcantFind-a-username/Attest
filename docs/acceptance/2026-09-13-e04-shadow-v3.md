# E-04 shadow, stratum v3 — 29 pull requests, 0 published, and a zero that means nothing yet

**Owner instruction, phase 2 of the 2026-09-13 window.** *Count the recent reviewable pull
requests of your own live repositories, estimate the cost, reserve it, then run a prospective
shadow review that writes no remote comment. Zero false publications is the only pass. One line
of result per pull request.*

Study: [`benchmarks/studies/e04-prospective-v3`](../../benchmarks/studies/e04-prospective-v3),
protocol frozen at `7e141545861dda89` **before any unit ran**. Spend **$1.793201** of the
**$6.00** reserved. Data:
[`trials-local-host.jsonl`](../../benchmarks/studies/e04-prospective-v3/trials-local-host.jsonl).

## 0. The answer, and it is not the one the numbers first suggest

**29 of 29 units ran. 223 candidates, 33 eligible, 24 reproductions attempted, 0 certified,
0 published — and all 24 reproduction attempts failed for the same mechanical reason**:

```
isolation backend unavailable: environment bootstrap failed
(python 3.13, roots [...]): the image build timed out after 897.5 s
```

So **no publication was reachable on this host**, and a run in which nothing could be published
does not establish that nothing wrong was published. That is the sentence D-177 exists to force,
and it applies to this study exactly as it applies to a review:

> A silence over an executor that never ran is not "nothing met a bar."

`G-SHADOW-001` says the same thing in its own pass conditions — *all-silence fails utility
regardless of precision*. **This stratum therefore does not pass the gate, and the owner's
condition is met only vacuously.** The measurement is re-taken on the declared CI platform
(§5), where the executor works.

**The product itself behaved correctly throughout.** Each of the 24 is a recorded DEFER naming
its own reason; nothing was claimed, nothing was hidden, and the failure is visible in the
ledger without anyone looking for it.

## 3. Where the 24 attempts went, and why it is one number

| failure category | count |
|---|---|
| `environment bootstrap failed` | **24** |
| everything else | **0** |

Not 23 and one other. **Every** reproduction this study attempted died in the same place, on both
clones and at two interpreter versions:

```
environment bootstrap failed (python 3.13, roots ['.']):
    the image build timed out after 897.529 s
environment bootstrap failed (python 3.13, roots ['services/adviser_layer', ...]):
    the image build timed out after 897.986 s
```

### 3.1 The host, diagnosed rather than guessed

Four observations, in order:

1. `docker run --rm python:3.13-slim` **works**, and a container on this host reaches
   `https://pypi.org/simple/six/` and gets a `200`. Container networking is fine.
2. `ensure_image` on the same tree with `remaining_s=3600` **still fails**, at the builder's own
   internal ceiling: *"the image build timed out after 1800 s"*. Thirty minutes is not enough
   either.
3. A build of a two-line Dockerfile — `FROM python:3.13-slim` then `pip install six`, with the
   base image **already present locally** — hangs for over ninety seconds at
   `#2 [internal] load metadata for docker.io/library/python:3.13-slim`.
4. The build cache holds **77.8 kB**. The failed builds got far enough to cache essentially
   nothing.

So it is buildkit's **registry metadata resolution** that hangs on this host, not the product,
not the trees, and not container networking. Every reproduction image build must resolve its
base image before it can install anything, so every one of the 24 timed out at the same step.

The same build takes **27.9 s** on a GitHub `ubuntu-latest` runner — that is measured, on this
project's own external receipt of 2026-09-12.

### 3.2 What this does and does not impeach

**It does not impeach the product.** No wrong claim was made, no silence was dressed up as a
clean bill of health, and the reason reached the ledger in full. It does not impeach any earlier
measurement either: every recorded run says which executor profile it used, and the runs that
certified used a working one.

**It does impeach this study's number.** `0 published` over a population where the publication
path was never open is not evidence about the publication rule, about D-199, or about safety.

## 4. What the gate says

| | |
|---|---|
| the owner's condition — zero false publications | **met, vacuously** — and a vacuous pass is not a pass |
| `G-SHADOW-001` | **FAIL** |

`G-SHADOW-001` fails on this stratum for three independent reasons, and only the first is about
the host:

1. **all-silence**, which its own pass conditions call a utility failure regardless of precision;
2. **scale** — its design asks for at least 500 pull requests across at least 30 repositories,
   at least 100 adjudicated shadow findings and at least 200 adjudicated silent units. The
   owner's entire account holds **29** reviewable pull requests across **6** supported
   repositories. This is not a budget problem and no amount of money fixes it;
3. **prospectivity** — one unit of 29 is genuinely prospective.

Reasons 2 and 3 are structural. **`G-SHADOW-001` cannot be passed by this account's traffic**,
and saying so is more useful than a number that pretends otherwise. What *can* be established is
mainline §1 condition 5 — *one prospective shadow run on the owner's live repositories has
produced no false publication* — and that needs the executor to work.

## 5. The re-take, on the platform the product ships to

`.github/workflows/e04-shadow.yml` (`workflow_dispatch`) runs **the same frozen sample** on
`ubuntu-latest`, where the registry resolves and an image builds in seconds. Nothing about the
study changes: the protocol digest, the population, the order, the drill exclusion and the
per-unit budget are the committed ones, and the driver still uses the local review path, so **no
GitHub client is constructed and no comment can be written to any repository**.

Two differences are declared rather than discovered:

- **`OneTapVocal` is private** and `GITHUB_TOKEN` cannot clone it, so the runner reports it
  **skipped by name**. Its local row is in §2 (13 candidates, 0 eligible) and it contributed no
  reproduction attempt on either host.
- The local trials are kept as `trials-local-host.jsonl` rather than deleted, so both columns
  stay readable and this report's §2 remains checkable.

## 6. What this report does not say

- **That the new publication rule is safe on real traffic.** That is the question the study was
  bought to answer and it is still open; §5 is how it gets answered.
- **That 29 pull requests would be enough if they had run.** §4 reason 2 says they would not be,
  for `G-SHADOW-001`. They are enough for mainline condition 5, which asks for one clean
  prospective run and not for a rate.
- **That the drills would have published.** They were excluded before the run and never
  reviewed; nothing here is evidence about them either way.
